# Demo survey — every stock TempleOS program against TempleOS/RISC-V

Generated by `tools/survey_demo_one.sh`. There is deliberately no commit stamp here: it would
name the commit the file was WRITTEN at, which is one before the commit that contains it, and
the numbers only come out of the tool as committed. Run the command to reproduce them:

```sh
find Demo -name '*.HC' | sort | xargs -P 4 -n 1 tools/survey_demo_one.sh > /tmp/survey.tsv
```

## Levels

| level | meaning |
|---|---|
| **L0-FAIL** | does not compile against the RV kernel |
| **L1-TRAP** | compiles and links, then FAULTS |
| **L1-HANG** | runs but does not finish inside the window |
| **L1-OK** | loads into a real image, boots, runs its own top-level code, reaches the end |

The harness boots a RAM-backed RedSea drive (`RVMountRAMDisk('B',8192)` + `RVHomeBringUp('B')`,
two lines out of `Kernel/KBootRV.HC`), so a demo that touches a file gets `File not found` and
not `throw('Drv')`. That alone took `Demo/DolDoc/FileRead.HC` and
`Demo/SortFileDemo/F64FileGen.HC` from L1-TRAP to running. Nothing is populated on it, so a
demo that reads a distribution file still fails — honestly, and by name.

`Demo/AcctExample/**` is a personal Home account and names six values that lived in its own `~/`;
`tools/survey_demo_one.sh` includes the placeholder set `tos/HomeAcctExample.HH` for that
directory and no other, so an L0 change there is partly a header this repo wrote. See
`docs/ACCT_EXAMPLE.md`.

**What L1 does not claim:** that a program does anything useful. Only four are driven with
scripted input and checked for a real response — Halogen, MassSpring, BattleLines and Lines
(`make kernel-game-{input,mouse,scanchar,lines}-smoke`). Everything else is untested above
"it runs".

Three harness mistakes had to be fixed before these numbers meant anything. Each had been
reported as a kernel bug first:

1. A demo ends with its own entry point as a top-level statement, so INCLUDING one RAN it.
   157 files now carry `#ifndef RV_NO_DEMO_AUTORUN` (141 + the 16 the first pass's pattern
   missed). `tools/guard_demo_autoruns.py` keeps it checkable.
2. The kernel has to be booted BEFORE the demo is included — a demo's top-level statements
   run at load and many print, and `PutS` dereferences `Fs`. Booting inside `main()` made
   **18 of 32 traps** fault in `PutS` before `main` ran. That alone took L1-OK 107 → 123.
3. The survey's own scratch directory was read from a stale run once, which put a `PutS`
   fault in this document that no current build produces. `tools/traploc.sh` reads `HOLYC_MAP`
   so a fault is a function name rather than a number to interpret.

## Two things to know before working the L0-FAIL list

**1. The ceiling is not 204.** Twelve demos contain x86 assembly in an `asm{}` block —
`Demo/Asm/*` (8 of them), `Demo/Lectures/FixedPointAdvanced.HC`, `Optimization.HC`, `Ring3.HC`,
and `Demo/Progress.HC`. The RISC-V assembler rejects those blocks whole, so the code is simply not
in the image. `Demo/Asm/AsmHelloWorld.HC` is the clearest case: its block is `PUSH RSI` /
`MOV RCX,10` / `CALL PUT_HEX_U8` / `LOOP @@05`, and the file ends with `Call(_HELLO_WORLD)`.

The survey records that one as L0-FAIL because `_HELLO_WORLD` is an `asm{}` label a statement
cannot name. **Do not "fix" that by making statements name asm labels.** The label belongs to a
dropped block, so the call would resolve to nothing, take a stub returning 0, and print nothing —
the demo would move from L0-FAIL to L1-OK while doing strictly less than before. These twelve
need their assembly translated, which is a different project from adding files to the PRJ.

**2. A file full of `extern` declarations makes things worse, not better.** `Adam/AExts.HC` looks
like the single highest-value addition: it names `DocMax` (3 demos) and `View` (2), and
`tools/check_prj_collisions.py` says it collides with nothing. It is 89 `extern` lines and **zero
bodies**. The PRJ compiles with `OPTf_EXTERNS_TO_IMPORTS` on, so every one of those names would
become an unresolved import that `bootstrap/holy_rt.h` stubs to a function returning 0 — see
`docs/ASM_PORTABILITY.md`. Several demos would compile and then silently do nothing.

The collision checker now warns about this, because "no collision" and "safe to add" are not the
same question. Screen a candidate on **bodies**, not on name clashes:

```sh
$ tools/check_prj_collisions.py Adam/AExts.HC
candidate(s) add no collision (72 PRJ files scanned)

WARNING — declarations only, so adding this defines NOTHING:
  Adam/AExts.HC   89 extern decl(s), 0 bodies -> 89 phantom import slot(s)
```

## Does not finish (L1-HANG)

Re-run at 40s with the whole serial log read, which splits them. Two former members of
this list, `Demo/Games/TheDead.HC` and `Demo/Games/BlackDiamond.HC`, were the harness
again: both end in `TheDead;` / `BlackDiamond;` followed by a DolDoc BINARY TAIL, so the
guard pass — which took the last non-blank line — never saw the call. `tools/hangpc.sh`
had TheDead spinning in `RVSnd`/`RVSndPcmFill` with `ra` in `JobsHndlr` — it was playing
its song. Both are L1-OK now. So is `Demo/MultiCore/Lock.HC`: `JobQue` returned NULL
(`ra=JobResGet+0x14c`, sampled three times over) until `Kernel/RVJob.HC` gave it a
single-hart implementation — which then exposed the `lock` newline bug.

Where a row below says what a program is doing rather than what it last printed, that came
from `tools/hangpc.sh`: QMP `info registers` three times a few seconds apart, each `pc`/`ra`
mapped through `HOLYC_MAP`. A hang never traps, so `tools/traploc.sh` cannot see it.

**A named compiler gap**

`Carry` is `public _intern IC_CARRY` in `Kernel/KernelB.HH`, `IC_CARRY` has no case in
`Compiler/OptPass_RV.HC`, and `host/parser.c` skips the intrinsic token — so it loads as an
unresolved import returning 0. RISC-V has no carry flag. `Demo/Carry.HC` printed 470,109
lines in 40s with `hi` never leaving zero, because `BigCnt` is `lo+=1<<58; hi+=Carry;` under
`while (hi<0x10)`.

| program | evidence |
|---|---|
| `Demo/Carry.HC` | infinite loop on a Carry of 0 |
